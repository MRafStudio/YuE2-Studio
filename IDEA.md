# YuE2-Studio - заметки проекта

## Правила стиля (наши, проверять при каждой правке)

- **Тире - только короткое `-`.** Длинные тире не используем нигде: ни в текстах интерфейса и i18n,
  ни в комментариях кода, ни в документации, ни в переписке. Речь о трёх символах: em dash
  (U+2014), en dash (U+2013), horizontal bar (U+2015). Короткое тире ставится с пробелами:
  `слово - слово`. Строки автора, которые мы переносим или переписываем, тоже приводим к короткому
  тире, но смысл и формулировки сохраняем; строки, которых мы не касались, не трогаем вовсе.
- Комментарии в коде - на английском (требование автора), интерфейсные строки - в i18n на пяти
  языках, личные файлы и инструменты - в `.rafstudio/` и `IDEA.md`.
- **Наши интерфейсные строки лежат в `app/i18n/yue2.ts`** (пять языков в одном файле). Файлы
  `en.ts`, `ru.ts`, `zh.ts`, `ja.ts`, `ko.ts` - авторские: там наши ключи не живут, их строки
  не трогаем. Перед правкой строки проверить адрес: `grep -n "<ключ>" app/i18n/*.ts`.

## Правила интерфейса (наши - проверять при каждой правке)

- **Модалки живут только на верхнем уровне окна** (в `App.tsx`, рядом с модалками автора). Модалка
  внутри страницы (`renderContent`) попадает в поддерево, которое React прячет (`Activity`), и
  «не открывается» без единой ошибки в консоли - так было с созданием сессии: из «Библиотеки» ее
  просто не было видно.
- **Технические состояния внутренних частей не показываем.** Для человека студия - одно
  приложение, а не набор сервисов: фраз вида «сервис сессий не отвечает» в интерфейсе быть не
  должно. Сбой показываем спокойным состоянием, без тревоги.
- **Студия многоязычна - это обязательное правило.** Интерфейс живёт на пяти языках
  (`en`, `ru`, `zh`, `ja`, `ko`), и любая строка, которую видит человек, идёт во все пять
  (`app/i18n/yue2.ts`, тип выводится из блока `en`, тест ловит пропуск). Это касается и строк,
  которые создаёт автоматика или агент: название сессии «Импорт», подсказки, предупреждения -
  тоже ключи i18n, а не английский литерал в коде.
- **Списки и счётчики не врут.** Число песен у сессии обязано совпадать со списком: связь
  «песня - сессия» берётся из состава самой сессии, а не из общей карты, где при дублировании
  побеждает последняя сессия (найдено 27.09, к исправлению).

Написание музыки, ремастеры и каверы, караоке с помощью YuE2-Studio - https://github.com/timoncool/YuE2-Studio.git

Ручной список (что именно проверяется):

   (`feat(studio): …`) **и осмысленное тело** - решение Рафа (30.09): «если автор ленив и не пишет

   он попадает в новости студии.
   Для справки, как пишет сам автор (проверено 30.09 по его 161 коммиту): без префиксов типа, тело

   (`app/data/changelog.json`) собирается скриптом `scripts/changelog.mjs` из заголовка и первого
   абзаца тела (вызов на `prebuild`/`predev` в `app/package.json`).
2. **В коммите - только исходники фичи.** Никаких личных файлов (этот `IDEA.md`), весов
   (`.gguf`, `.safetensors`, `.onnx`), медиа, баз, ключей, `node_modules/`.
3. **Комментарии в коде - английские.** Русские допустимы только внутри строк-переводов i18n.
4. **Никакого Python/Node и внешних файлов в рантайме** (правило из `AGENTS.md`). Данные для
   интерфейса приходят родным мостом студии (`useBridgeCommand`), а не из файлов на диске.
5. **Локализация на 5 языков**: `en`, `ru`, `zh`, `ja`, `ko` в `app/i18n/yue2.ts`

6. **Гейты репозитория зелёные**: `npx tsc --noEmit -p tsconfig.json` и `npx vitest run`.
7. **CHANGELOG руками не править** - он генерируется из git-истории.
8. Линтера в проекте нет; тесты компонентов автор не практикует (они есть у `services/` и `i18n/`).

## Инструменты - здесь же, в репе: папка `.rafstudio/`

Всё, что касается проекта, живёт в проекте: знания, решения и инструменты. Вернулись в репу -
прочитали её файлы, и всё понятно, ничего держать «в голове» не нужно. В ветке с фичей папка не
отслеживается (`.git/info/exclude`), поэтому в pull request не уходит; своя копия - в ветке
`rafstudio/tooling`.

| Файл | Зачем |
|---|---|
| `.rafstudio/preflight.py` | **проверка требований автора перед PR**: `python .rafstudio/preflight.py` → «READY» |
| `.rafstudio/restore.py` | восстановить правки этой ветки из патча в любой копии репы: `--root <копия>`, `--check` |
| `.rafstudio/notify.py` | журнал агента для человека (`.jsonl` + `.html` в `data` студии) |
| `.rafstudio/patches/` | патчи ветки (пересоздаются: `git format-patch upstream/main..HEAD -o .rafstudio/patches`) |
| `.rafstudio/components/` | копии компонентов этой ветки (для `restore.py`) |

**Обновление ветки `rafstudio/tooling`** (после новых правок): отдельная рабочая копия, копируем
туда `.rafstudio/` и `IDEA.md`, коммитим, пушим, копию убираем:

```bash
git worktree add ../YuE2-Studio-tooling -b rafstudio/tooling fc23f9a   # ветка main
cp -r .rafstudio IDEA.md ../YuE2-Studio-tooling/
cd ../YuE2-Studio-tooling && git add -f .rafstudio IDEA.md && git commit -m "chore(project): …" && git push origin HEAD
cd - && git worktree remove --force ../YuE2-Studio-tooling
```
В рабочей копии фичи эти файлы остаются неотслеживаемыми (`.git/info/exclude`) - иначе `preflight`
справедливо забракует pull request: у автора правило «в коммите только исходники фичи».

**Не переключать основную рабочую копию на ветку `rafstudio/tooling`** (грабля 29.09): при
переключении git удаляет отслеживаемые там файлы инструментов из рабочей копии, и они исчезают с
диска. Возвращать - только поштучно (`git show <ветка>:<путь> > <путь>`); `git archive <ветка> |
tar -x` перетирает свежие untracked-файлы (`IDEA.md`, `HANDOFF.md`) старыми версиями из ветки.

## Грабли: две сессии «Импорт» (разобрано 29.09, ИСПРАВЛЕНО)

Симптом: в списке сессий две «Импорт» с разным содержимым (6 и 18 треков), созданы с разницей

не проверяла, а флаг `importedOnce` сбрасывается при перезагрузке окна. Два окна на один сервис

**Как исправлено (коммит в этой же смене):**
- служба помечает свою сессию в новой таблице `session_kinds` (`kind='import'`) - идентификатор,
  а не имя; имя автосессии в базе ПУСТОЕ, слова рисует окно по i18n (`sessionImportName`);
- ручка `POST /v1/workspaces/import` (`Library::adopt_import_workspace`): в одной транзакции
  находит помеченную сессию, иначе усыновляет старую по списку имён, иначе создаёт, и добирает
  всех сирот - идемпотентно, поэтому гонка двух окон больше не даёт двух сессий;
- окно больше не ищет по имени: шлёт ручке все пять локализованных написаний (для старых
  библиотек) и показывает имя автосессии через `sessionTitle`; поиск в списке тоже идёт по
  отображаемому имени;
- `update_workspace` снимает маркер, если человек дал сессии имя: названная сессия становится
  обычной, и следующая автосборка заводит новую, а не пишет в чужую;
- тест `tracks_made_outside_a_session_are_gathered_once` (служба) закрывает все четыре случая.

## Куда складывать треки агента (требование Рафа, 29.09)

Правило человека, а не догадка машины:

- Сказал **«генерируй каждую песню в свою сессию»** - на каждую песню делается **новая сессия**.
- Сказал **«всё в одну»** - все треки ложатся в **текущую** сессию.
- Агент **не угадывает** «активную» сессию: сессию выбирает человек.

Когда агенту не ясно, куда складывать (прямо не сказано), он **не угадывает, а спрашивает
модалкой в окне** - три варианта:

1. «Каждый трек в новую сессию» - на каждый трек своя сессия (имена делает служба).
2. «Все новые треки сложить в текущую сессию» - всё в ту, что открыта.
3. «Все новые треки сложить в новую сессию» - с полем для имени сессии.

Порядок работ (решение Рафа): **сначала в коде**, скилл MCP правим, когда заработает.

**СДЕЛАНО 29.09** (коммит `74bd26b`): сервис принимает `session` (`each` / `current` / `new:<имя>`) у
девяти генераторов, окно спрашивает модалкой `SessionChoiceModal` (один вопрос на пакет, «запомнить»
на 15 минут тишины или «всегда» в `agent_settings.session_choice`), трек ложится в НАЗВАННУЮ сессию,
а не в открытую. **Скилл агента обновлён** (коммит `57e14be`, `docs/mcp-skill.md`): три слова
`session`, «нет сессии и никто не выбрал - не работаем», правило «после задачи проверь
`workspace_get`, где трек лежит на самом деле». **Живая проверка в окне пройдена 29.09:**
exe собран и подменён, модалка появилась, ответ человека (имя новой сессии) увёл оба трека
пакета в неё, «каждой песне - своя сессия» дал три сессии по именам треков, «всегда» отключило
вопрос. Факты - в HANDOFF. Следы проверки убраны, настройка сброшена.

### Решения (Раф, 29.09)

1. Генераторы получают параметр **`session`**: `each` (каждому треку своя сессия) /
   `current` (в открытую сессию) / `new:<имя>` (все в новую с этим именем).
2. Модалка с выбором показывается **только когда сессия не указана явно**.
3. Пакет спрашивается **один раз** на все треки («пять песен - один вопрос»).
4. Сессии, созданные по режиму `each`, называются **именем песни**.
5. Ответ помнится: **на текущий пакет** (до конца работы агента) и умеет **«всегда»** -
   так же, как поводок.

### План работ (сначала код, скилл - после)

1. **Сервис** (`crates/music-server/src/lib.rs`, `mcp.rs`): у генераторов (`song_create`,
   `song_replay`, `stems_split`, `score_*`, `processing_start`, `karaoke_make`,
   `midi_transcribe`, `library_import`) появляется `session` в схеме; разбор
   `each | current | new:<имя>` делается рядом с поводком (`agent_may`): `each` - каждому
   треку своя сессия с именем трека, `current` - открытая, `new:<имя>` - одна новая на пакет.

2. **Модалка** (`AgentConfirmModal.tsx` или новая `SessionChoiceModal.tsx`): три варианта -

   новую сессию» (поле имени) + «запомнить»; вопрос и ответ идут в журнал «Сообщения».

## Сессии: правила для агента (в дорожную карту, 29.09)

  1. Генерация и разделение должны принимать **явную сессию** (`workspace_id`), а не

  2. Агент обязан проверять **факт** принадлежности трека (`workspace_get`), а не только

## Нет сессии - нет трека (требование Рафа, 27.09)

Работа идёт **только внутри сессии** - ровно как у агента (MCP): сначала сессия, потом всё
остальное. Причина найдена живьём: трек, созданный из окна, сохранялся в библиотеке, но к
сессии не привязывался (`POST /v1/music/jobs` сессию не проверял), а список на странице
«Создать» показывает треки сессии - человек видел «Трек готов» и не находил трека.

Сделано (27.09):

- **Кнопка «Создать»**: перед генерацией спрашивает у сервиса активную сессию
  (`ensureSessionForGeneration` в `app/App.tsx`); сессии нет - открывается окно создания
  сессии, а сам запрос ждёт (`pendingGenerateRef`) и выполняется сразу после её создания.
- **Шлагбаум в сервисе**: `session_open(state, what)` в `crates/music-server/src/lib.rs`
  возвращает `409` с текстом «no session is open: …» для ручек генерации, разделения на стемы,
  караоке, обработки, MIDI-транскрипции и импорта аудио.
- **Готовый трек входит в открытую сессию**: после импорта в библиотеку
  (`add_song_to_workspace`) - иначе он лежит «за спиной» открытой сессии и его не видно.

Правило на будущее: любой новый генератор (в окне или у агента) обязан пройти `session_open`,
а окно - спросить сессию до запроса, а не после.

## Повторное разделение: старый набор стемов в архив, новый - сразу (требование Рафа, 27.09)

Сегодня `stems_into_library` (`crates/music-server/src/lib.rs`) при повторном разделении песни
**удаляет** её прежние стемы - и записи, и файлы («новые уже в библиотеке, потом уходят старые»).
Должно быть иначе:

1. Вызвав «сгенерируй новый стем» для песни, у которой стемы уже есть, **старый набор из всех шести
   инструментов не удаляем, а убираем в архив** с меткой времени создания набора:
   `СТЕМ-2026-09-27 20:08:03` (время есть у каждой записи - колонка `songs.created_at`).
2. **Новый набор создаётся тут же и снова для всех шести инструментов** (drums, bass, vocals,
   guitar, piano, other) - как и было задумано.
3. Основа всего этого - маркеры в БД: `metadata.derived = { from, from_title, tool: "stems",
   settings: { stem, model, overlap } }`. По ним отличаем архивный набор от действующего и партию
   от полной песни (общий модуль `app/components/songParts.tsx`: `isPart`, `partName`, `partLabelKey`).
   Имя партии берём из `settings.stem` (его даёт разделитель), а не из заголовка: заголовок сервис
   пишет латиницей и он не локализуется.

**СДЕЛАНО 27.09** (коммиты `4660fcd`, `791eabf`): таблица `stems_archive`, файлы уезжают в
`<media>/stems-archive/<song_id>/<batch_slug>/<stem>.wav`, ручка `GET /v1/library/stems-archive`,
при повторном разделении старый набор остаётся целым набором из шести партий, а новый создаётся сразу.

**Метка набора (29.09):** в БД лежит момент набора (`2026-09-27 11:34:49`) - без слов; слово «СТЕМ»
рисует окно из i18n. Старые библиотеки, где метка была написана словами одного языка, исправляются
сами при открытии (`Library::read_sets_of_stems_without_words` в `open_at`, идемпотентно).

### Как это устроено (решение Рафа, 27.09)

Архив - это **отдельная таблица**, а не то же дерево с пометкой: у каждого архивного стема
обязательна связь с исходной песней, от которой он рождён. Файлы при этом уезжают в
**отдельную папку**.

```sql
CREATE TABLE IF NOT EXISTS stems_archive (
    id            TEXT PRIMARY KEY,  -- запись архива
    song_id       TEXT NOT NULL,     -- ИСХОДНАЯ песня: связь с songs.id
    song_title    TEXT NOT NULL,     -- её имя на момент архивации
    batch         TEXT NOT NULL,     -- метка набора: «СТЕМ-2026-09-27 20:08:03»
    batch_slug    TEXT NOT NULL,     -- она же для пути: STEM-2026-09-27_20-08-03
    stem          TEXT NOT NULL,     -- кто он: drums|bass|vocals|guitar|piano|other
    title         TEXT NOT NULL,     -- заголовок архивного трека
    audio_path    TEXT NOT NULL,     -- файл в папке архива
    duration_secs REAL,
    created_at    TEXT NOT NULL,     -- когда набор был создан (из songs.created_at, тот же формат)
    archived_at   TEXT NOT NULL      -- когда уехал в архив
);
```

Файлы: `<media>/stems-archive/<song_id>/<batch_slug>/<stem>.wav` - отдельная папка, имя набора
латиницей и без пробелов (кириллица и пробелы в путях - источник бед), а человеческое
«СТЕМ-2026-09-27 20:08:03» живёт в БД и показывается в интерфейсе.

Порядок при повторном разделении: собрать прежний набор по маркерам (`derived.from` = песня,
`tool` = stems, `settings.stem`), унести его файлы и записи в архив, и только потом творить новый
набор - снова из всех шести инструментов. Так ни один старый стем не теряется, а связь с
исходником не рвётся.

## Почему у партии (стема) убраны пункты из контекстного меню

Решение проекта (`732a397`, `9baf44e`) - чтобы не «вернуть как было» потом:

1. **Технически бессмысленно.** Стем - уже результат разделения: у барабана нет своих барабанов,
   баса и вокала, отделять от него нечего. Повторное разделение - это «копии копий»: мусор в
   библиотеке, лишние файлы на диске и минуты счёта на GPU.
2. **У партии нет своего промпта.** Она не рождалась из style+lyrics, поэтому «Повторить промпт»
   подставил бы промпт родителя (или пустоту), а «Перерендерить» пересоздал бы не то, что видно на
   экране. Это уже не бесполезно, а вводит в заблуждение.
3. **Продукт не должен показывать тупики.** Формулировка требования: «такой пункт меню должен либо
   отсутствовать в принципе (предпочтительно), либо хотя бы не быть доступным».
4. **Скрываем, а не `disabled`.** Скрытие - уже паттерн автора (караоке появляется только при
   выполнении условий); серый пункт без пояснения читается как поломка интерфейса.
5. **В панели «Инструменты» - текст, а не пустота** (`stemsPartCannot`): тот список трека общий для
   MIDI, редактора, обработки и транскрипции, где партия - нормальный выбор, и «выключенная» кнопка
   выглядела бы как сбой.
6. **Что осталось и почему:** редактор, видео, MIDI, партитура, скачать, удалить, в плейлист -
   всё это работает с партией как с обычным аудио.

Все входы закрыты (их было три!): меню трека, панель «Инструменты», панель «Детали песни»
(там же лежал легаси-путь через `demucs-web` - `extractStems`). Признак партии берётся из БД:
`metadata.derived.tool === 'stems'` → `isPart(song)` в `app/components/songParts.tsx`.

**Сборка своей версии интерфейса (кратко).** Rust + MSVC нужны только для exe: `rustc/cargo`
стоят в пользовательском профиле Windows (`%USERPROFILE%\.cargo`), а НЕ в папке, которую может
перезаписать установщик. `npx tauri build --no-bundle` из `desktop/` собирается ~4 минуты и кладёт
`desktop/src-tauri/target/release/YuE2-Studio.exe` (~61 МБ, интерфейс вшит). Своя сборка
копируется в портативную папку студии рядом с оригинальным `YuE2-Studio.exe` под именем
`YuE2-Studio-raf.exe` (оба держим для сравнения). Грабли MSYS (PATH по `:`,
RUSTUP_HOME/CARGO_HOME только нативно) - в скилле `yue2-studio-build`. **Собирать и запускать
exe - только по прямому указанию владельца студии.**

## Режимы «поводка» для агента (решено)

Три ступени, переключаются в «Настройки → Agent (MCP)»:

1. **«Свободно»** - как у вендора: агент делает что угодно, без вопросов. Удобно, когда следишь
   за окном.
2. **«Поводок по опасному»** - **дефолт**: свободно читать, искать и генерировать новое;
   спрашивать на удаление, перезапись существующего, закрытие сессии и разделение чужого трека.
3. **«Поводок на всё»** - подтверждение на каждую операцию; для отладки и незнакомых агентов.

Решения агента и ответы пользователя попадают в панель «Сообщения». Реализация - этап C3
(команда моста «подтверди» + настройка режима).

**Доступ агента к данным окна.** Строки песен несут метку `song <id>: <название>`, и агент видит
их в дереве окна; строки сессий теперь несут такую же - `session <id>: <имя>`. Без метки сессию
приходилось искать по её месту в списке, что хрупко. Тот же приём применять и к новым спискам.

## Концепция: Workspace = «сессия работы»

**Замысел:** рабочее пространство - это сессия, внутри которой собирается всё, что связано с текущей
работой. Сессия живёт сколько угодно, может содержать сотни треков с партиями (стемы), MIDI, караоке,
референсы - всё, что делается на странице «Создать». Завершение сессии - перенос её в архив
(библиотека всех воркспейсов). Файлы при этом никуда не переезжают: у объектов просто есть `workspace_id`.

**Решено:**

| Вопрос | Решение |
|---|---|
| Что показывает SongList на «Создать» | Только активную сессию; переключение «Сессия / Библиотека» - кнопками на панели **АЛЬФА** |
| Треки вне сессии | Сессия обязательна ВСЕГДА: нет активной - MCP-агент и генерация требуют создать сессию (с именем) либо возвращают ошибку |
| Сколько сессий | Одна активная; список сессий открывается кнопкой на панели АЛЬФА - активировать существующую или создать новую |
| Порядок в списке сессий | **Активная - всегда первой строкой** (потом остальные по дате создания) - просьба Рафа, коммит `721d0a7` |
| Удаление сессии агентом | `workspace_delete` есть, но помечено необратимым: спрашивает человека |
| Вопрос об удалении | Один: «Удалить» или «Отменить» - никаких «разрешить для сессии / спрашивать каждый раз / запрещать всегда» (коммит `313e093`). Остальные необратимые действия спрашивают по-прежнему |
| Кому задаётся вопрос | **Окну, в котором человек работает** (последнему, что заявило о фокусе), а не тому, что позже подключилось. Касается ВСЕХ модальных вопросов (коммит `a708a5c`) |
| Два окна при разработке | Приложение (Tauri) и браузер dev-UI (`:3791`) подписаны оба; до `a708a5c` вопрос уходил последнему подписавшемуся и «прыгал» между ними |
| Порядок сессий | Активная - первой строкой в списке (коммит `721d0a7`) |
| Вопрос агента | Приходит окну, где человек работает (`/mcp/window/focus`, коммит `a708a5c`): при разработке подписаны два окна - приложение и браузер `:3791` |
| Сортировка списков | Одна кнопка-слово перед заголовком: «По дате создания» → «По дате изменения» → «По имени песни» (в сессиях - «По имени сессии»), рядом стрелка направления. Выбор общий для списков и запоминается (`localStorage.listOrder`, коммиты `236c437`, `f643dff`) |
| Даты в строках | Трек: «Создан ДД.ММ.ГГГГ, ЧЧ:ММ» и - если был лайк - «Последняя реакция» (коммит `40c6ecc`). Сессия: «Создана … · Изменено …» |
| Что значит «реакция» | Только лайк: он пишет `metadata.liked_at` и не двигает дату изменения трека. Переименование, обложка, караоке, выбор версии - правки, а не реакции |
| Что меняет сессию | Изменение её содержимого: трек добавлен, удалён или отредактирован внутри неё (`touch_sessions_with` в `library.rs`). Лайк сессию не двигает |
| Кнопка «Обновить» | Самая левая в панели АЛЬФА, без подписи: перечитывает библиотеку, плейлисты и сессии вручную (коммит `b49f970`) - лечит exe, где события «что-то изменилось» теряются |
| Пагинация сессий | Список сессий читается страницами, как песни: 10 (или своё число) на страницу + листалка (коммит `8798eda`) |
| Обозреватель сессий | Пятая вкладка **«Сессии»** на странице «Библиотека» (Все песни / Понравившиеся / Плейлисты / **Сессии** / Импорт) - порядок задан Рафом: сессии стоят перед импортом (коммит `b22570e`) |
| Пагинация списков | Кнопки листания стоят **над** списком (не под ним) и по центру между соседями: «Все песни», «Понравившиеся», «Плейлисты», «Сессии» (коммит `8eaa866`) |
| Переключение сессий | Активировал другую - **старая остаётся открытой**; в архив только по кнопке «Закрыть сессию» |
| Уникальность имени | **Автосуффикс** при коллизии: «Рок», «Рок (2)», «Рок (3)» |
| Старые треки (7 шт.) | При первом запуске **создать сессию «Импорт»** и привязать к ней всё существующее |
| Стемы в списке | **Свёрнуты под родительской песней**; при раскрытии - сдвиг вправо (~1 см), а в освободившемся месте иконки стемов (бас, гитара, барабаны, пиано, вокал, прочее) |
| Лайки | **Перенести в БД** (привязать к песне) - переживут смену профиля и машины |

**Терминология (принята):**

- Кнопка завершения - **«Закрыть сессию»** (не «отправить в архив»).
- В списке сессий у каждой - кнопка **«Открыть сессию»**, делающая её активной.
- **Открытая сессия = текущая.** Все остальные - закрытые. Открыта всегда одна.
- **Флаг «нет открытой сессии»** = нет идентификатора активной сессии → генерация через MCP
  невозможна, требуется сначала открыть/создать сессию (ошибка с таким текстом).

**Подтверждение генерации из MCP (важно):**

Даже когда сессия открыта, MCP-запрос на создание трека должен сначала прийти в студию
**модальным окном**, где пользователь подтверждает создание в текущей сессии или отклоняет.
Варианты ответа:

- **Разрешить один раз** - только этот трек;
- **Разрешить всегда для этой сессии** - больше не спрашивать в рамках открытой сессии;
- **Выбрать другую сессию** - переключиться и создавать в ней;
- отклонить (трек не создаётся).

**Как это реализуемо (проверено в коде):** готовой команды «спроси пользователя» у моста НЕТ
(в `useBridgeCommand` есть только `notify`, `create_*`, `player_*`, `library_*`, `video_*`,
`equalizer_*`, `visualizer_*`, `winamp_*`, `navigate`, `open_settings`). Но есть всё нужное,
чтобы добавить по-авторски: UI-компонент `ConfirmDialog` (уже используется в `App.tsx`),
паттерн моста `useBridgeCommand` и серверный `Bridge` (`broadcast` + ожидание ответа окна
через `oneshot`). Значит: новая команда моста + новый MCP-инструмент, а окно рисует модалку.

**Технические решения (минимум новых сущностей, без миграций):**

- **Таблица `workspaces`** через `CREATE TABLE IF NOT EXISTS` (`id`, `name`, `description`,
  `created_at`, `updated_at`, `closed_at`; `closed_at IS NULL` = открытая, иначе архив).
- **Привязка песни к сессии** - метка `workspace_id` в `metadata_json` (как автор хранит всё
  расширяемое), а не новая колонка: миграция не нужна, старые библиотеки подхватываются сами.
- **Лайки** - `liked` в `metadata_json` той же песни (одна точка хранения, не плодим таблицы).
- **Существующие лайки** из `localStorage` (`yue2-studio-liked-song-ids`) один раз переносятся в БД.
- **MCP**: добавить инструменты `workspace_list`, `workspace_create`, `workspace_open`,
  `workspace_close`, `workspace_get`; `song_create` и прочие генераторы без активной сессии -
  ошибка с просьбой создать сессию.
- **Стем-иконки** (lucide): барабаны, бас, гитара, пиано, вокал, прочее.

**Панель АЛЬФА** (верхняя панель над SongList): кнопка списка сессий + переключатель
«Сессия | Библиотека» + колокольчик (журнал сообщений) + разделители.

**Ширина списков (решено):** ограничение ширины колонки оставляем (длинные строки текста плохо
читаются на широком экране), но **центрирование убрано** - карточки прижаты к левому краю колонки,
как и панель АЛЬФА с поиском (`w-full min-w-0 max-w-5xl`, без `mx-auto`).

**Идея на будущий разбор дизайна:** на очень широких экранах (2K/4K) карточки не растягивать,
а **добавлять справа постоянно открытые полезные панели** - то есть использовать ширину под
инструменты, а не под удлинение строк.

**Архитектурная опора концепции (проверено в коде):**

- одна БД `library.sqlite`, файлы в `data/media|midi|karaoke`, связь по `song_id` - ничего не переезжает;
- производные уже связаны с родителем через `metadata.derived.from` - сессия накрывает стемы, MIDI,
  караоке и версии аудио каскадом;
- миграций у автора нет by design (`CREATE TABLE IF NOT EXISTS` + расширения в `metadata_json`) -
  таблицу сессий добавляем тем же способом, старые библиотеки подхватят её сами;
- пагинации нет ни в сервисе, ни в UI - ещё один довод, что список на «Создать» = активная сессия.
  (Пагинация списков сделана 29.09 - `Pager.tsx`, размер страницы в настройках.)
